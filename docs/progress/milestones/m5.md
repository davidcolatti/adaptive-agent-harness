## Deviations from the plan

- **The plan's eight `FallbackReason`s replace M4's six** rather than living beside them — two
  closed vocabularies for one stored field is exactly the text-matching problem a closed union
  exists to prevent. ADR-0044.
- **`low_confidence` and `missing_evidence` are unreachable from the runtime by design.** They are
  policy outcomes: a decision that could not be obtained at all is not a low-confidence one, because
  no judgment was made. M3's policy layer is what raises them, on a judgment whose confidence falls
  below its band.
- **`FallbackContext.completedNodes[].output` was added beside `outputRef`**, carrying every listed
  node's validated output inline rather than a reference alone, capped at 64 KiB total. The plan's
  section 5 names only the reference; across the one channel a fallback actually has — a model
  reading `clientContext`, not a process holding a `Storage` handle — a reference alone would have
  made the full agent unable to reuse anything, which is exactly what M5-T5 requires it to do.
  `trusted` still governs how a value may be used, not whether it is shown; an untrusted `agent`
  node's output is present specifically because withholding it would withhold the expensive thing
  the fallback exists to reuse. ADR-0044.
- **`escalate` nodes are not listed in `completedNodes`.** They produce a `FallbackContext` rather
  than a value, so an `outputRef` pointing at nothing would be worse than an omission.
- **The router is an `AgentRuntime` composition; `createHarness()` gained no `router` option.** That
  is how "the same harness call can execute either workflow or full agent" holds without core
  learning about workflow versions, which it structurally cannot (`registry` sits beneath `core` in
  the dependency diagram). ADR-0044.
- **The fallback envelope travels through `ExecutionContext.fallback` and eve's documented
  turn-scoped `clientContext`** (under a harness-owned `harness.fallback` key), rather than through
  a new dedicated channel. eve documents the transport; the key and shape under it are harness-owned
  and carry references, flags and (capped) output — never an unredacted tool result.
- **A workflow version's status change and its promotion-ledger row are two PostgREST statements,
  not one transaction.** PostgREST offers no cross-statement transaction, so the residual failure
  mode is a status change whose ledger row never gets written. Recorded rather than fixed with a
  client-side retry that could not actually restore atomicity.
- **`shadow` and `canary` are legal `WorkflowStatus` values that never route traffic.**
  `selectCompatibleWorkflow()` refuses every non-`active` version with `not-active`; only `active`
  serves a job. A shadow/canary rollout policy is not part of this milestone.
- **`pnpm harness workflow list` was not built.** `Storage.listWorkflowVersions()` exists, but the
  CLI addition needs a new parsed command, filter flags, a renderer and its own tests — not the
  "small addition" the task made it conditional on. The CLI's target-list marker now reads
  `not yet implemented (M5 landed the storage read)`.
- **`asAgentRuntime()` keeps its escalated-to-failed mapping**, for standalone use outside the
  router; it is now documented as the honest record of "nowhere to go" rather than a stopgap that
  needed replacing.
- **`runs.jev_calls` is now a real, non-zero measurement** for a workflow run that made decisions,
  counted at the engine call site (including a call that throws). The column's own SQL comment
  still calls it a placeholder, because migrations are append-only and never hand-edited after the
  fact; `docs/contracts/storage.md` is the corrected authority.
